# CONVENTIONS.md — Reca Naming and Code Conventions

Reca does not enforce these conventions — the language allows any structure.
This document describes the chosen model for the Canon Aria and Python bootstrap.

---

## Naming Prefixes

| Prefix | Meaning | Rule |
|--------|---------|------|
| `C_` | Numeric constant | Only in `constants.re` |
| `K_` (generated) | Layout/memory constant | `generated/layout.re`, e.g. `K_AETHER_SIZE`. Generated by `gen_compiler.py`. Do not edit manually. |
| `K_` (hand-written) | Stable-pointer register | `alloc.re`/`limiter.re`, e.g. `K_CURSOR`. See "Region Modifiers" below — `NEW`/`WAX_NEW` auto-carries SAVE+LOCK. |
| `RA_` | Runtime register (volatile) | Scratch — not preserved across calls. `NEW X` (word=0). |
| `SC_` | Exire slot | Changed at runtime via Exire. `NEW X` (word=0). |
| `SYS_` | Exire number | `SYS_WRITE`, `SYS_READ`, etc. |
| `SF_` | String fragment (compiler emit) | Byte-chain Lux for IR generation. `SET X "..."` |
| `Yaku_X` | Compile rule for Aspect X | Linked graph for generating IR instruction X. |

`*_OUTER` slots (function-private RA_LINK save locations) are **no longer used**.
RA_LINK is saved/restored automatically by the call stack (`RA_SP`) on every
`Voca`/`Redi` — see `registers.re`. Non-leaf subroutines need no special
bookkeeping.

---

## NEW vs NEWREF

| Command | word | When |
|---------|------|------|
| `NEW X` | 0 | Register luces (RA_*, SC_*, scratch luces) |
| `NEWREF X` | addr(X) | Identity/relation luces — their word is used in comparisons |

**Identity luces** (must use NEWREF): `Op`, `El1`, `El2`, `Exit`, `Next`, `Entry`, `Yaku`,
`ACCORD_USE`, `LIMITER_ACCORD`, `AutoNext`, `ForType`, `SelfYaku`.

## Region Modifiers (OWN / SAVE / LOCK / ...)

`NEW X In1=REGION` (`In2=`/`In3=`/... for more than one at once) places `X`
in a named region. **Any string works** — there is no fixed vocabulary a
region name has to come from. `_name_regions` (loader.py) stores whatever
strings real declarations actually use, and placement (`_combo_key`,
`_combo_blocks` — names sharing a combo colocate in one reserved block)
works identically regardless of which strings those are. "OWN"/"SAVE"/"LOCK"
are simply the three strings the project happens to use today:

| Region | Means | Cost if wrong |
|--------|-------|----------------|
| `OWN` | Per-thread locality (Pattern W) | None — placement-only, harmless either way |
| `SAVE` | Guaranteed allocation, never elided as "unused" | None — a couple of spare luces at worst |
| `LOCK` | Ordinary `Write`/any op's `Exit` may not target this address — only `Key` may | **A raised `LockViolation`** at the exact write, if legitimate code forgot to use `Key` |

A region string having any consequence *beyond* placement (LOCK's write
guard is the one example) is a separate, explicit thing some other piece of
code specifically recognizes — nothing here gatekeeps which strings are
"real". Adding a fourth region for some new purpose needs no new
vocabulary entry, just (if it needs runtime behavior at all) one more
explicit check somewhere, the way `_lock_ranges` checks for `'lock'`.

**Clearing**: `In{N}=0` on a *numbered* slot clears only whatever region
that exact slot last set for this name — `loader.py`'s `_region_slot_role`
remembers, per name and per slot number, which region string was written
there, so a later `In1=0` knows to undo specifically that one, leaving
every other region the name carries untouched. Bare `In=0` (no number)
clears everything at once, unconditionally, regardless of what bare `In=`
itself may have set. The two are deliberately asymmetric: by convention,
bare `In=` is reserved for the "clear all" sentinel — real assignments
should use a numbered slot, precisely so they stay individually undoable
later. (The old three-name-specific negation vocabulary — `FREE`/`UNSAVE`/
`UNLOCK` as values, and `OWN`/`FREE`/`SAVE`/`UNSAVE`/`LOCK`/`UNLOCK` as
standalone commands, plus the original `X | OWN` tail syntax — is gone:
all of it duplicated what `SET X In{N}=REGION` / `In{N}=0` already say, and
none of it scaled past exactly three known region names.)

### Auto-inferred by name prefix

- **`RA_` + `NEW`/`WAX_NEW`** → OWN, unless overridden with `In{N}=0`.
- **`K_` + `NEW`/`WAX_NEW`** → SAVE **and** LOCK, unless overridden with
  `In{N}=0` on whichever slot carries the one being opted out of.

Both rules exist because the prefix itself already declares the name's role
(per-thread scratch register; foundational, project-wide bookkeeping state)
— the region modifier just makes that declaration's consequence real instead
of leaving it as a comment someone has to remember to add by hand. SAVE is
safe to auto-apply everywhere (failure-free even where not needed). LOCK is
**not** failure-free where wrong — but the failure is a loud, immediate
exception naming the exact offending address, not silent corruption, which
is exactly the guardrail LOCK exists to provide. A K_ name that turns out to
need ongoing writes (like `K_CURSOR`) is *supposed* to surface that need
immediately, by throwing, so its author reaches for `Key` —
not to fail silently by never having been protected in the first place.

### Key: LOCK's authorized writer

`Key` is the only opcode exempt from the LOCK guard — dispatch via it, at
the one declared call site that legitimately needs to write to protected
memory, **is** the authorization (no separate authorized-code region, no
per-NOVA flag, nothing else checked). Which write *shape* a given `Key`
instruction performs is resolved per-instance, at runtime, not by which
opcode name got dispatched — every Key instruction's own `SLOT_OP` is
always literally `Key`:

- **`Op=Key`** (no `Op1=`) — Write's shape (double indirection through El1:
  writes to `aether[aether[El1]]`). This is what every `K_`-style
  double-deref stable-pointer register needs (`K_CURSOR`, `K_WATERMARK`,
  `K_TRACE_POS`, `K_FLUX_CURSOR`, `K_FLUX_FREELIST` — see their updaters in
  alloc.re, iris.re, yaku.re, arena.re).
- **`Op=Key Op1=Move`** — Move's shape (single indirection via Exit: writes
  to `aether[Exit]` directly), for LOCK-protected data that isn't
  double-deref-shaped, where Write's shape wouldn't even address the right
  cell. `Op1` is a genuine extra-lumen relation on the instruction (same
  `[Name][N]=` convention as any other), read back by
  `interpreter.py`'s `_resolve_key_shape` the first time that instruction's
  own `pc` is dispatched, and memoized in `_key_shape` from then on — the
  *shape choice* is a fixed, cacheable property of a given `pc` (as long as
  its own operands stay unrewritten), but the write itself always re-runs
  every time, exactly like `Write`. An unrecognized `Op1` target raises
  `KeyShapeError` immediately, rather than silently guessing. A third shape
  (`Op1=Add`, say) is one more small handler in `interpreter.py`'s
  `_resolve_key_shape` when a real need for it shows up — not pre-built
  combinatorially ahead of any actual use.

Reading from a LOCK-protected address is never restricted — only writing
(any op's `Exit` landing inside a locked range, or `Write`'s own El1-derived
target) is. `_lock_ranges` (interpreter.py) is what's actually checked at
write time; it's rebuilt from `loader.py`'s `_combo_blocks` (any combination
containing `'lock'`, whatever else it's combined with) every time Wave 1
runs, so it stays correct even as new LOCK'd names are discovered mid-load.
`Key` itself never reaches that check at all (in any of the three execution
loops) — it's special-cased at dispatch, same as `Write`, and routed
through `_exec_key` instead.

## Lumen Scanning

```re
// Scan a Data lux (lumina at offset=1):
WALK_ONE name  RA_LUX_REG  Entry     // RA_SR_OUT = exit lux where rel=Entry

// Scan a NOVA lux (extra lumina at offset=SLOT_PAD=6 -- extras, when
// present, start right at the pad slot itself, not after it):
WALK_NOVA name  RA_NOVA_REG  Op        // RA_SR_OUT = exit lux where rel=Op
```

Use `WALK_NOVA` when RA_LUX holds a NOVA lux with extra LINK lumina.
Use `WALK_ONE` for Data luces.

---

slot next, Lumen(Next), and Lumen(AutoNext)

Three different things share the word "Next." Each exists for a different reader and is written by different code — conflating them is the most common source of confusion when investigating control flow.

1. slot next ("SLOT_NEXT", slot 5) — the only thing the interpreter reads.

Not a Lumen: a fixed-position raw field, no name, no scan.

"0" means "my successor is physically adjacent, fall through" (the Line path, free — see "LANGUAGE.md"'s Line/Warp/Flux).

Any other value is an address the interpreter jumps to directly (Warp).

Filled two ways:

- Implicit — sequential NOVA luces without "NOLINK" in between are auto-chained by "_chain_nova"/"_link_novas" (Wave-B): "_link_novas(prev, nxt)" writes "aether[prev+SLOT_NEXT] = nxt", but only if "nxt" isn't physically adjacent (adjacent luces just stay "0").

- Explicit — "NOVAE"'s "Next=N" parameter wires the synthesized NOVA's slot next directly (see "NOVAE" below).

NOVA A Move ...
// A's slot next = B (or 0, if physically adjacent)

NOVA B Equal ...
// B's slot next = C (or 0)

NOLINK
// break — C gets no auto-chain from B

NOVA C Jump ...
// C's slot next = 0

2. Lumen(rel=Next) — a real, scannable graph edge ("LINK X Next Y"), independent of slot next and not written by the auto-chain.

Used when a tool that only walks lumina (BFS, a dataflow scheduler) needs to discover a control-flow edge that the auto-chain wouldn't produce here — e.g. "yaku.re"'s "LINK P0_INIT_C Next RT_BUILD_ENTRY", added specifically so BFS reaches that entry statically.

3. Lumen(rel=AutoNext) — an optional annotation, added only if the "auto_link.re" aria is loaded, alongside every implicit slot-next write from case 1.

Marks "this control-flow edge came from text adjacency, not declared intent" — the distinction a walker otherwise can't recover, since slot next alone doesn't record where its value came from.

Explicit writes (NOVAE's "Next=N", a hand-written "LINK X Next Y") never get an AutoNext lumen: they're already known-intentional.

If the aria isn't loaded, case 3 never happens and nothing else changes — the interpreter only ever reads slot next (case 1) regardless.
```

## Registries

- **LUX_REGISTRY** — all Data luces. Scanned by P0_SCAN, LIMITER, ACCORD.
- **NOVA_REGISTRY** — all NOVA luces. Scanned by EMIT_FUNC (compiler BFS).

An NOVA lux that is also an entry point (has `LINK X Entry Yaku`) appears in **both**
registries. Use `WALK_NOVA` to read its extra LINK lumina.

## Comment Syntax

### Single-line: `/`

A line starting with `/` is a comment — the entire line is ignored.

```
/This is a comment — the whole line is ignored
```

Works because `/` is not a registered command, so the loader skips the unrecognised
token to end of line.

### Inline block: `//...//`

`//` opens a comment block, the next `//` closes it. The block is **cut from the
stream** — code before and after it is read normally. Blocks may span multiple lines.

```
//cut// OK OK         ← both OKs execute
OK //cut// OK         ← both OKs execute
OK OK //cut
OK OK//               ← all four OKs execute; block spanned a line
```

The block closes at the first `//` encountered — anywhere on the line.

### What does NOT exist

- Inline `/` in the middle of a line does not open a single-line comment:
  `OK /no OK` — `/no` is treated as an unknown command (skipped), but the parser still sees it.
- `///` and longer — **not** the same as `//`. Exactly two slashes, not three or more.

### Command-like words inside prose: quote them

`check_comments.py` flags any comment line whose first word matches a real
command/macro name (`NOVA`, `NEW`, `SET`, `FOR`, `LINK`, ...) — this is how
it catches a missing closing `//` swallowing real code. But documentation
prose legitimately starts sentences with these words sometimes ("Set via
Move before Exire...", or showing example syntax like "NEW MyNote"). Wrap
the word in quotes to silence the false positive without weakening the
check elsewhere:

```
/"NEW" MyNote                              ← was: NEW MyNote
/"Set" via Move before Exire; ...          ← was: Set via Move before Exire; ...
/"For" each lux with Entry→Yaku, ...       ← was: For each lux with Entry→Yaku, ...
```

The quoting is purely textual (breaks `text.split()[0] == 'NEW'`), it
doesn't change what the comment says. Every flagged line found so far has
been individually verified safe (read the surrounding `//` block, confirm
it's actually closed) before quoting — don't quote a flagged line on
sight without checking it first; the check exists to catch real bugs too.
